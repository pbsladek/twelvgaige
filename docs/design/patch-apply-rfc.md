# Patch Apply RFC

Status: draft accepted for implementation planning

Owner: authoring-management track

Related plan: `docs/design/authoring-completion-plan.md`, phase AC0

## Summary

`patch_apply` is the first proposed write-capable agent-authoring primitive.
It must not apply natural-language suggestions. It only applies a structured,
digest-bound patch artifact that was generated by a read-only authoring flow,
reviewed by a human, approved against the exact patch hash, and verified against
the current files before writing.

The command is deliberately file-oriented and daemon-free. It operates inside a
resolved traphouse root, writes through sibling temporary files, validates every
candidate shell, and reruns lint after changes. If any safety check fails, no
write should happen.

## Non-Goals

- No automatic application of model text.
- No arbitrary shell command execution as part of patch application.
- No binary file patching.
- No patching outside the resolved traphouse root.
- No implicit approval from workflow lifecycle metadata.
- No partial trust in path strings supplied by the model.
- No runtime behavior changes. Patch application edits authoring files only.

## Threat Model

`patch_apply` must assume the patch artifact may be malicious or stale, even if
it came from a Twelvgaige authoring round.

Threats:

- Path traversal through absolute paths, `..`, Unicode ambiguity, or symlinks.
- Stale patch application after the reviewed file changed.
- Approval reuse against a different patch.
- Model-generated edits to hidden files, config files, or unrelated source.
- Binary payload injection.
- Validation bypass through unsupported file formats.
- Time-of-check/time-of-use races between digest verification and write.
- Multi-file partial apply leaving the traphouse in an invalid state.
- Human confusion caused by non-deterministic patch summaries.

Controls:

- All paths are root-relative, normalized, and rechecked after expansion.
- Absolute paths and parent traversal are rejected before filesystem access.
- Symlink path components and non-regular target files are rejected.
- Original file digests must match before any candidate write.
- Patch approval binds to the canonical patch digest.
- Writes use sibling temporary files and atomic replacement.
- Candidate files are validated and linted before replacement.
- Post-write digests are verified.
- Multi-file application is ordered and reported deterministically.

## Artifact Format

Patch artifacts are JSON. YAML/TOML may be supported later, but the first
implementation should accept JSON only to keep canonicalization and hash
binding straightforward.

Top-level schema:

```json
{
  "kind": "twelvgaige.patch.v1",
  "id": "patch_20260503_001",
  "created_at": "2026-05-03T20:00:00Z",
  "root": {
    "type": "traphouse",
    "path_hint": "traphouse"
  },
  "generated_by": {
    "tool": "patch_plan",
    "provider": "mock",
    "model": "mock",
    "round_id": "round_optional",
    "actor": "agent:shell_shot_editor"
  },
  "files": [
    {
      "path": "workflows/incident.yaml",
      "kind": "workflow",
      "operation": "replace",
      "before_digest": "sha256:...",
      "after_digest": "sha256:...",
      "before_size_bytes": 1234,
      "after_size_bytes": 1456,
      "content": "kind: workflow\nid: incident\n..."
    }
  ],
  "validations": [
    {"command": "shell validate", "path": "workflows/incident.yaml"},
    {"command": "shell lint", "path": "workflows/incident.yaml", "strict": true}
  ],
  "summary": {
    "changed_files": 1,
    "changed_shots": ["verify_recovery"],
    "safety_implications": ["adds safety gate before apply_remediation"]
  },
  "patch_digest": "sha256:..."
}
```

Canonical patch digest:

- Exclude `patch_digest` from the digest input.
- Encode JSON with stable map key ordering.
- Preserve file `content` exactly as a string.
- Hash canonical bytes with SHA-256.
- Store as lowercase `sha256:<hex>`.

File entries:

| Field | Required | Notes |
| --- | --- | --- |
| `path` | yes | Root-relative path below the resolved traphouse root. |
| `kind` | yes | `workflow`, `agent`, `shot_template`, `scaffold`, `library_lock`, or `doc`. |
| `operation` | yes | First implementation supports only `replace`. |
| `before_digest` | yes | Digest of current file contents. |
| `after_digest` | yes | Digest of proposed `content`. |
| `before_size_bytes` | yes | Expected current size. |
| `after_size_bytes` | yes | Proposed content size. |
| `content` | yes for replace | Complete replacement content. |

Allowed first-pass file kinds:

- `workflow`: `workflows/**/*.yaml`, `workflows/**/*.yml`,
  `workflows/**/*.json`, `workflows/**/*.toml`
- `agent`: `workflows/agents/**/*.yaml`, `workflows/agents/**/*.yml`,
  `workflows/agents/**/*.json`, `workflows/agents/**/*.toml`
- `shot_template`: `shots/**/*.yaml`, `shots/**/*.yml`, `shots/**/*.json`,
  `shots/**/*.toml`
- `scaffold`: `scaffolds/**/*.yaml`, `scaffolds/**/*.yml`,
  `scaffolds/**/*.json`, `scaffolds/**/*.toml`
- `library_lock`: `twelvgaige-library.lock`,
  `twelvgaige-scaffold-library.lock`
- `doc`: `README.md`, `usage.md`, `docs/**/*.md`

The first implementation should reject `create`, `delete`, `rename`, and binary
patches. Those can be added after replace semantics are proven.

## Approval Binding

Patch approval is separate from workflow execution approval. Workflow lifecycle
approval says a shell may run. Patch approval says a specific file edit may be
written.

Approval record:

```json
{
  "kind": "twelvgaige.patch_approval.v1",
  "id": "approval_20260503_001",
  "patch_digest": "sha256:...",
  "approved_by": "human:platform-owner",
  "approved_at": "2026-05-03T20:05:00Z",
  "scope": "repo",
  "expires_at": "2026-05-04T20:05:00Z",
  "evidence_hash": "sha256:...",
  "reason": "Reviewed generated authoring patch"
}
```

Approval rules:

- `patch_digest` must exactly match the candidate artifact.
- `approved_by` must be present and must not start with `agent:`.
- `scope` must be `file`, `repo`, or `ci`.
- `expires_at`, when present, must be in the future.
- `evidence_hash`, when present, should bind to an external review artifact,
  PR, ticket, or signed attestation.
- Approval cannot be inferred from `metadata.approved` on a workflow shell.

First-pass CLI may accept approval as a JSON file:

```bash
twelvgaige shell patch apply patch.json --approval approval.json --write
```

Later versions may add `shell patch approve patch.json --by <actor>` to create
approval files, but apply must still verify the approval digest.

## Command Surface

Inspect:

```bash
twelvgaige shell patch inspect <patch-file> [--root <path>] [--format human|json]
```

Behavior:

- Parses the patch.
- Computes canonical `patch_digest`.
- Prints changed files, file kinds, sizes, digests, and validations.
- Does not require approval.
- Does not inspect current target files unless `--root` is supplied.

Verify:

```bash
twelvgaige shell patch verify <patch-file> [--approval <approval-file>] [--root <path>] [--format human|json]
```

Behavior:

- Runs all inspect checks.
- Requires a root when verifying file state.
- Verifies paths, file kinds, symlinks, current digests, proposed digests,
  approval digest when provided, and candidate validation/lint.
- Does not write.
- Exits non-zero on any finding with severity `error`.

Apply:

```bash
twelvgaige shell patch apply <patch-file> --approval <approval-file> --write [--root <path>] [--format human|json]
```

Behavior:

- Requires `--write`.
- Requires approval.
- Runs verify first.
- Writes candidate files through sibling temp files.
- Verifies final digests.
- Runs post-write validation/lint.
- Emits an apply report with changed files and final digests.

No dry-run apply shorthand should write. If `--write` is omitted, `apply` should
return the same report shape as `verify` and state that no files were changed.

## Path And Filesystem Rules

Each patch file path is interpreted relative to the resolved traphouse root.

Reject:

- absolute paths
- empty paths
- paths containing `..`
- paths whose normalized expanded path is outside root
- symlink path components
- existing target that is not a regular file
- hard-linked targets when link count can be detected and is greater than 1
- binary content
- content exceeding configured max bytes
- file kinds not matching allowlisted path globs

For new file support later, parent directories must already exist unless the RFC
is extended with explicit directory creation semantics.

## Validation Pipeline

For every candidate file before write:

1. Parse artifact JSON.
2. Canonicalize and verify `patch_digest`.
3. Resolve traphouse root.
4. Normalize and classify all target paths.
5. Verify original target files exist and are regular files.
6. Reject symlink traversal.
7. Verify current `before_digest` and size.
8. Verify proposed `after_digest` and size.
9. Decode candidate file by kind and extension.
10. For shell files, run `Twelvgaige.validate_shell/1` against candidate
    content through an in-memory or temp-file validation path.
11. For workflow shells, run strict lint against candidate content where
    possible; otherwise write to a temporary validation directory under root and
    lint there.
12. Verify all requested validation commands are known safe commands.
13. Produce deterministic findings.

For write:

1. Repeat verify immediately before writing.
2. Write temp siblings.
3. Rename into place.
4. Verify final digests.
5. Run post-write validation and strict lint.
6. Emit audit/checkpoint events where the current audit system is available.

## Multi-File Semantics

First implementation should use all-or-refuse preflight:

- Verify every file before writing any file.
- If any preflight check fails, write nothing.
- Apply files in sorted path order.
- If a write fails mid-apply, stop immediately and return a partial-failure
  report with files written, files skipped, and the exact reason.

Rollback is not required in the first implementation because atomic replacement
does not provide a portable multi-file transaction. The report must be explicit
about partial success. Future work may add best-effort rollback using captured
before contents when file sizes are below a configured threshold.

## Audit Events

Patch commands should emit structured events when an audit sink is available:

- `authoring.patch.inspect`
- `authoring.patch.verify`
- `authoring.patch.apply.start`
- `authoring.patch.apply.file_written`
- `authoring.patch.apply.complete`
- `authoring.patch.apply.failed`

Event payload:

- patch ID
- patch digest
- approval ID and approval actor when present
- root
- file paths
- before and after digests
- validation findings
- command actor when known

Audit failure must not hide apply failure. In a later hardened phase, policy may
require audit success before write.

## Error And Exit Code Contract

Human output must state:

- whether files were changed
- patch digest
- approval status
- refused findings
- changed paths
- validations run

JSON output must include:

```json
{
  "status": "ok",
  "exit_code": 0,
  "errors": [],
  "patch_digest": "sha256:...",
  "approval": {"status": "valid"},
  "files": [],
  "findings": [],
  "changed": false
}
```

Exit code guidance:

- `0`: inspect/verify/apply succeeded.
- `1`: verification failed or post-write validation failed.
- `4`: invalid input, invalid patch artifact, invalid approval, or path denial.
- `7`: partial apply failure after at least one file was written.

## Test Plan

Unit tests:

- canonical patch digest excludes `patch_digest`
- path normalization rejects absolute paths and `..`
- kind/path classifier accepts only allowed globs
- approval digest match and mismatch
- approval expiry
- binary content rejection
- before/after digest verification
- unsupported operation rejection

CLI tests:

- `shell patch inspect` prints patch summary without root.
- `shell patch verify` catches current file digest mismatch.
- `shell patch verify --approval` catches approval mismatch.
- `shell patch apply` without `--write` writes nothing.
- `shell patch apply --write` replaces a workflow file and validates it.
- JSON output is stable.

Filesystem tests:

- rejects symlink target
- rejects symlink parent component
- rejects target outside root
- temp file cleanup after failed write
- partial apply report when injected write failure occurs

Integration tests:

- read-only authoring round produces a patch plan artifact
- human approval file binds to patch digest
- apply writes patch
- `shell validate`, `shell lint --strict`, and `shell graph` succeed after apply

## Implementation Phases

1. Patch schema and canonical digest module.
2. Patch inspect CLI.
3. Root/path/kind verification.
4. Approval verification.
5. Candidate validation and lint preflight.
6. Apply with atomic sibling writes and digest verification.
7. Audit events and partial-failure reporting.
8. Hosted authoring integration that emits `twelvgaige.patch.v1` artifacts.

## Open Follow-Ups

- Whether approval files should support cryptographic signatures in addition to
  digest binding.
- Whether multi-file rollback is worth the added complexity.
- Whether docs edits should be allowed in the first implementation or delayed
  until shell-only patching is proven.
- Whether `patch_plan` should evolve from advisory change descriptions to full
  `twelvgaige.patch.v1` artifact generation, or whether a separate
  `patch_build` command should do that conversion.
